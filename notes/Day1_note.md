## 🎯 วัตถุประสงค์การเรียนรู้ประจำวัน

เมื่อจบการอบรมวันที่ 1 ผู้เรียนจะสามารถ:

1. อธิบายความแตกต่างระหว่าง **Monitoring** กับ **Observability** และเสาหลักทั้งสาม (Metrics, Logs, Traces) ได้
2. อธิบายบทบาทของ **APM** และ **Error Tracking** ในวงจรการดูแลระบบงาน CRM / ERP ได้
3. อธิบายสถาปัตยกรรมของ Sentry ตั้งแต่ **SDK → DSN → Relay → Ingest → UI** และหน้าที่ของแต่ละส่วนประกอบได้
4. อธิบายข้อกำหนดระบบ ส่วนประกอบ และแผนการดูแล **Self-hosted Sentry** ได้ เพื่อเตรียมลงมือติดตั้งจริงในวันที่ 3
5. สร้าง Organization, Team, Project และเข้าใจความหมายของ **DSN, Environment, Release** ได้
6. ตั้งค่า **Data Scrubbing / PII Protection** ให้เหมาะกับข้อกำหนดของระบบงานธนาคารได้
7. ฝัง `sentry-spring-boot-starter-jakarta` เข้ากับแอป Spring Boot ของระบบงานจำลอง แล้วยืนยันว่า Error เข้าสู่ Sentry ได้จริง (Workshop Day 1)

> **หมายเหตุสำคัญของหลักสูตรนี้:** ตลอด 3 วันเราจะพัฒนาและ Monitor ระบบงานจำลองตัวเดียวต่อเนื่องกันคือ **BCEL CRM Lite** ซึ่งเป็นระบบงาน CRM/ERP ย่อส่วน ประกอบด้วย Spring Boot (Backend) + Angular (Frontend) + MariaDB (Database) โดยใช้ **ข้อมูลจำลองทั้งหมด ไม่มีข้อมูลลูกค้าจริงของธนาคาร** เด็ดขาด

### 1.1.2 Monitoring กับ Observability ต่างกันอย่างไร

สองคำนี้มักถูกใช้สลับกัน แต่ความหมายต่างกันในเชิงปฏิบัติอย่างมีนัยสำคัญ

| ประเด็น | Monitoring (การเฝ้าระวัง) | Observability (การสังเกตได้) |
| --- | --- | --- |
| คำถามที่ตอบได้ | "ระบบพังหรือยัง" (known-unknowns) | "ทำไมถึงพัง" (unknown-unknowns) |
| วิธีทำงาน | ตั้ง Metric + Threshold ไว้ล่วงหน้า | เก็บข้อมูลบริบทเข้มข้น แล้วตั้งคำถามใหม่ได้ตลอด |
| ตัวอย่าง | CPU > 80% ให้แจ้งเตือน | "ทำไมเฉพาะลูกค้า segment `PREMIER` ที่สาขา 05 ถึงกดปุ่ม Export แล้ว Error" |
| ข้อจำกัด | ถามคำถามใหม่ไม่ได้ ต้องรอ Deploy ใหม่ | ต้องออกแบบการเก็บข้อมูลให้ดี ไม่งั้นเปลืองที่เก็บ |

```
Monitoring:                          Observability:
┌──────────────────────────┐        ┌──────────────────────────────┐
│ ตั้งคำถามล่วงหน้าไว้แล้ว   │        │ ตั้งคำถามใหม่ได้ตอนเกิดปัญหา  │
│  - CPU สูงไหม            │   ⟶   │  - Error นี้กระทบใครบ้าง       │
│  - Service ยังตอบไหม     │        │  - เกิดหลัง Release ไหน       │
│  - Disk เต็มไหม          │        │  - Query ไหนที่ทำให้ช้า        │
└──────────────────────────┘        └──────────────────────────────┘
     "ไฟแดงติดหรือยัง"                    "ไฟแดงติดเพราะอะไร"
```

> 💡 **สรุปสั้น ๆ:** Monitoring บอกว่า **"มีอะไรผิดปกติ"** ส่วน Observability บอกว่า **"ผิดปกติเพราะอะไร"** องค์กรที่ดีต้องมีทั้งคู่ ไม่ใช่เลือกอย่างใดอย่างหนึ่ง

### 1.1.3 เสาหลักสามต้นของ Observability

| เสาหลัก | คืออะไร | ตอบคำถามว่า | ตัวอย่างในระบบ CRM |
| --- | --- | --- | --- |
| **Metrics** | ตัวเลขที่วัดตามช่วงเวลา (time-series) | "แย่แค่ไหน / บ่อยแค่ไหน" | Request/นาที, P95 latency, Error rate |
| **Logs** | ข้อความเหตุการณ์ที่มี timestamp | "ตอนนั้นเกิดอะไรขึ้น" | `ERROR CustomerService - customer not found: C0042` |
| **Traces** | เส้นทางของ 1 request ข้ามหลายบริการ | "ช้า/พังที่ชั้นไหน" | คลิกปุ่ม → `GET /api/customers/42/summary` → 18 SQL queries |

**P95 Latency** 
คือ ค่าความหน่วง (Latency) หรือเวลาตอบสนองของระบบในระดับเปอร์เซ็นไทล์ที่ 95 ซึ่งหมายความว่า 95% ของคำขอ (Requests) ทั้งหมดใช้เวลาประมวลผลน้อยกว่าหรือเท่ากับค่านี้นี้ โดยตัดกลุ่มที่ช้าที่สุดออกไป 5%

**ทำไมต้องใช้ P95 Latency?**
- ดีกว่าค่าเฉลี่ย (Average): ค่าเฉลี่ยอาจถูกบดบังด้วยคำขอส่วนใหญ่ที่เร็ว แต่ไม่สะท้อนปัญหาเมื่อมีบางคำขอที่ช้ามาก
- กรองค่าผิดปกติ: ช่วยตัดกลุ่มคำขอที่ช้าผิดปกติออกไป 5% สุดท้าย เพื่อให้เห็นภาพประสบการณ์ของคนส่วนใหญ่ในระบบอย่างแท้จริง
- ใช้วัดประสิทธิภาพระบบ: ทีมพัฒนาและวิศวกร (SRE) นิยมใช้ตั้งเป้าหมาย (SLO) เพื่อดูว่าบริการโดยรวมมีความเสถียรและเร็วพอสำหรับผู้ใช้งานเกือบทั้งหมดแล้วหรือยัง

**ตัวอย่างความเข้าใจ**
หากระบบแจ้งว่า **P95 Latency = 200 มิลลิวินาที (ms)** แปลว่า จากคำขอทั้งหมด 100 ครั้ง มี 99 หรือ 95 ครั้งที่ตอบกลับภายใน 200 มิลลิวินาทีหรือเร็วกว่านั้น จะมีเพียง 5 ครั้งที่เหลือที่อาจใช้เวลามากกว่า 200 ms


```
1 Request เดินทางอย่างไร และเสาหลักไหนเห็นอะไร:

  [Angular]        [Spring Boot]              [MariaDB]
     │                   │                        │
     ├── HTTP POST ─────>│                        │
     │                   ├── SELECT customer ────>│
     │                   │<───────────────────────┤
     │                   ├── SELECT account x15 ─>│  ⟵ N+1 ซ่อนอยู่ตรงนี้
     │                   │<───────────────────────┤
     │<── 200 OK ────────┤
     │
  └────────────────── 1 TRACE (2.4 วินาที) ──────────────────┘
       Metrics เห็น: "P95 = 2.4s" (รู้ว่าช้า แต่ไม่รู้ทำไม)
       Logs เห็น:    "query executed" x16 (เห็นเยอะ แต่ไม่รู้ว่าเกี่ยวกัน)
       Traces เห็น:  "SELECT account ถูกเรียก 15 ครั้งใน request เดียว" ✅
```

> ✅ **จุดสำคัญ:** Trace คือสิ่งที่ **ร้อยเรียง** Metrics และ Logs เข้าด้วยกันเป็นเรื่องเดียวกัน นี่คือเหตุผลที่หลักสูตรนี้ให้น้ำหนักกับ Distributed Tracing มาก (ทั้งวันที่ 2)

### 1.1.4 บทบาทของ APM และ Error Tracking

| ด้าน | Error Tracking | APM (Performance Monitoring) |
| --- | --- | --- |
| สนใจ | ระบบ **พัง** | ระบบ **ช้า** |
| หน่วยข้อมูล | Event / Issue | Transaction / Span |
| คำถามหลัก | "Exception นี้เกิดกี่ครั้ง กระทบใคร" | "Endpoint ไหนช้าสุด เพราะอะไร" |
| ผลลัพธ์ที่ได้ | Stack trace + Breadcrumbs + User | Waterfall ของ Span + P50/P95 |

Sentry ทำ **ทั้งสองอย่างในเครื่องมือเดียว** และที่สำคัญคือ **เชื่อมโยงกัน** เช่น เมื่อคลิกดู Error หนึ่งตัว จะเห็นลิงก์ไปยัง Trace ของ request นั้นได้ทันที นี่คือจุดแข็งหลักที่ทำให้เราเลือก Sentry ในหลักสูตรนี้

### 1.1.5 ภาพรวมเครื่องมือในตลาด และเหตุผลที่เลือก Sentry

| เครื่องมือ | จุดแข็ง | ข้อจำกัดสำหรับ BCEL |
| --- | --- | --- |
| **Sentry (Self-hosted)** | Error + Performance + Replay ครบในตัว, Self-host ได้เต็มรูปแบบ, SDK ครอบคลุม Java/Angular | ไม่ใช่ Infra monitoring (ต้องเสริม Prometheus) |
| Datadog APM | ครบเครื่องมาก ทั้ง Infra + APM + Log | SaaS อย่างเดียว ข้อมูลออกนอกองค์กร |
| New Relic | UI ดี วิเคราะห์ลึก | SaaS เป็นหลัก ราคาสูง |
| Elastic APM | Self-host ได้ รวมกับ ELK | ต้องดูแล Elasticsearch เอง หนัก |
| Prometheus + Grafana | มาตรฐาน Infra/K8s metrics | ไม่ใช่ Error tracking ไม่มี Stack trace |

> ✅ **สรุปการตัดสินใจ:** BCEL มีข้อกำหนดเรื่อง **Data Sovereignty** (ข้อมูลต้องอยู่ในองค์กร) จึงตัดตัวเลือก SaaS ออก และเราต้องการ **Error Tracking ระดับโค้ด** ซึ่ง Prometheus ทำไม่ได้ Sentry Self-hosted จึงตอบโจทย์ที่สุด โดยแนะนำให้ **เสริม Prometheus + Grafana** สำหรับ Infra/K8s metrics ในภายหลัง (จะกล่าวถึงตอนท้ายวันที่ 3)

> 📖 **อ้างอิง:** เอกสารเปรียบเทียบขอบเขต Self-hosted กับ SaaS ของ Sentry อ่านได้ที่ [develop.sentry.dev/self-hosted](https://develop.sentry.dev/self-hosted/) หัวข้อ "Differences between self-hosted and SaaS"

### 1.2.1 Sentry คืออะไร และครอบคลุมงานด้านใดบ้าง

Sentry เริ่มต้นจากการเป็น Error Tracking แต่ปัจจุบัน (เวอร์ชัน 26.x) ครอบคลุม 6 ด้านหลัก:

| ผลิตภัณฑ์ | หน้าที่ | ใช้ในหลักสูตรนี้ |
| --- | --- | --- |
| **Issues (Errors)** | รวบรวม จัดกลุ่ม และวินิจฉัย Exception | วันที่ 1–2 |
| **Tracing (Performance)** | วัด Transaction / Span ข้ามบริการ | วันที่ 2 |
| **Session Replay** | ย้อนดูหน้าจอที่ผู้ใช้เห็นก่อนเกิดปัญหา | วันที่ 3 |
| **Releases & Release Health** | ติดตามคุณภาพของแต่ละรอบ Deploy | วันที่ 3 |
| **Dashboards / Discover** | สร้างมุมมองและสืบค้นข้อมูลเชิงลึก | วันที่ 3 |
| **Profiling / Logs** | เจาะลึกระดับโค้ดและรวมศูนย์ log | วันที่ 3 (แนะนำ) |

> ⚠️ **สิ่งที่ Sentry ไม่ใช่:** Sentry **ไม่ใช่** ระบบ Infrastructure Monitoring มันไม่บอกว่า CPU ของ Node ไหนเต็ม, Pod ไหน OOMKilled, หรือ Disk ของ MariaDB เหลือเท่าไร งานเหล่านั้นเป็นของ Prometheus + Grafana / Zabbix ให้มองว่า Sentry ดูแล **"ชั้นแอปพลิเคชัน"** ส่วนอีกชุดดูแล **"ชั้นโครงสร้างพื้นฐาน"**

### 1.2.2 สถาปัตยกรรมภาพใหญ่: SDK → DSN → Relay → Ingest → UI

```
 [ แอปของเรา ]                          [ Self-hosted Sentry ]
 ┌────────────────┐                     ┌──────────────────────────────────┐
 │ Spring Boot    │                     │  nginx (:9000)                   │
 │  + sentry SDK  │──┐                  │     │                            │
 └────────────────┘  │                  │     ├──> web (Django UI + API)   │
 ┌────────────────┐  │   HTTPS + DSN    │     │                            │
 │ Angular        │──┼─────────────────>│     └──> relay ──> kafka         │
 │  + sentry SDK  │  │   (envelope)     │                      │           │
 └────────────────┘  │                  │                      v           │
 ┌────────────────┐  │                  │                  ingest-consumer │
 │ Jenkins        │──┘                  │                      │           │
 │  + sentry-cli  │                     │        ┌─────────────┼─────────┐ │
 └────────────────┘                     │        v             v         v │
                                        │   PostgreSQL    ClickHouse   Redis│
                                        │   (metadata)     (events)   (queue)│
                                        │        ^                          │
                                        │        └── worker (celery beat)   │
                                        └──────────────────────────────────┘
```

| ส่วนประกอบ | หน้าที่ | ถ้าล่มจะเกิดอะไร |
| --- | --- | --- |
| **SDK** | ดักจับ Error/Span ในแอป แล้วห่อเป็น "envelope" ส่งออก | ไม่มีข้อมูลเข้าเลย |
| **DSN** | สตริงที่บอก SDK ว่า "ส่งไปที่ไหน และเป็นของโปรเจกต์ใด" | ส่งผิดโปรเจกต์ / ส่งไม่ออก |
| **Relay** | ประตูหน้าด่าน ทำ rate limit, กรอง PII, บัฟเฟอร์ | Event ตกหล่นเมื่อโหลดสูง |
| **Kafka** | คิวกลาง รับ event เข้าคิวก่อนประมวลผล | ข้อมูลค้าง ไม่ขึ้นหน้าจอ |
| **Snuba / ClickHouse** | เก็บและค้นหา event จำนวนมหาศาล | ค้นหา/กราฟใช้ไม่ได้ |
| **PostgreSQL** | เก็บ metadata (org, project, user, rule) | ระบบล็อกอินและตั้งค่าใช้ไม่ได้ |
| **Redis** | คิวงานและแคช | งานเบื้องหลังไม่ทำงาน |
| **Worker** | ประมวลผลเบื้องหลัง (แจ้งเตือน, cleanup) | Alert ไม่ส่ง, ข้อมูลเก่าไม่ถูกลบ |
| **Symbolicator** | แปลง Stack trace ที่ถูก minify/compile ให้อ่านได้ | Source map ไม่ทำงาน |

> 💡 **ทำไมต้องรู้เรื่องนี้:** เมื่อ Workshop วันที่ 1 ทำแล้ว "Error ไม่ขึ้นใน Sentry" เราจะไล่ตรวจตามลำดับนี้ได้ทันที: SDK ส่งออกไหม (ดู `debug=true`) → DSN ถูกไหม → Relay รับไหม (`docker compose logs relay`) → Consumer ทำงานไหม (`docker compose logs ingest-consumer`)

### 1.2.3 แนวคิดสำคัญที่ต้องแยกให้ออก

```
Organization (bcel)
   │
   ├── Team: crm-dev
   │     ├── Project: bcel-crm-backend   (platform: java-spring-boot)
   │     │      ├── DSN: https://<key>@sentry.bcel.local/2
   │     │      ├── Environment: development | staging | production
   │     │      └── Release: bcel-crm-backend@1.4.0
   │     │
   │     └── Project: bcel-crm-frontend  (platform: javascript-angular)
   │            ├── DSN: https://<key>@sentry.bcel.local/3
   │            └── Release: bcel-crm-frontend@1.4.0
   │
   └── Team: erp-dev
         └── Project: bcel-erp-backend
```

| แนวคิด | ความหมาย | หลักการตั้งค่าที่แนะนำ |
| --- | --- | --- |
| **Organization** | หน่วยสูงสุด = องค์กร | 1 องค์กร 1 instance ก็เพียงพอ |
| **Team** | กลุ่มคนที่รับผิดชอบร่วมกัน | แบ่งตามทีมจริง เพื่อให้ Alert ไปถูกคน |
| **Project** | หน่วยที่รับ event = 1 แอป/1 บริการ | **แยกโปรเจกต์ระหว่าง Backend กับ Frontend เสมอ** เพราะ Stack trace, Alert และ Release คนละแบบ |
| **Environment** | บริบทการรัน | ใช้ชื่อมาตรฐาน: `development`, `staging`, `production` เท่านั้น อย่าให้แต่ละคนตั้งเอง |
| **Release** | เวอร์ชันของโค้ดที่ Deploy | รูปแบบ `<project>@<version>` เช่น `bcel-crm-backend@1.4.0` |
| **DSN** | ที่อยู่ + กุญแจสาธารณะของโปรเจกต์ | เป็นค่า **public** (ฝังใน JS ได้) แต่ไม่ใช่ Auth Token |

> ⚠️ **จุดที่คนสับสนบ่อยที่สุด:** **DSN ≠ Auth Token**
> - **DSN** ใช้ "ส่ง event เข้า" เท่านั้น ฝังใน Angular bundle ที่ผู้ใช้ดาวน์โหลดได้ ไม่ถือเป็นความลับร้ายแรง (แต่ควรมี rate limit)
> - **Auth Token** ใช้ "อ่านข้อมูล/สร้าง Release/อัปโหลด Source Map" **เป็นความลับ ห้ามฝังใน Frontend เด็ดขาด** ต้องเก็บใน Jenkins Credentials หรือ Kubernetes Secret เท่านั้น (เรียนวันที่ 3)

### 1.2.4 โครงสร้าง DSN แบบละเอียด

**แบบ Self-hosted** (ที่ BCEL จะใช้จริง)

```
https://a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6@sentry.bcel.local/2
└─┬──┘ └──────────────┬───────────────┘ └───────┬───────┘ └┬┘
scheme          public key                    host      project id
```

**แบบ SaaS** (ที่เราใช้ในห้อง Lab)

```
https://a1b2c3d4e5f6a7b8c9d0e1f2a3b4c5d6@o4509876543210.ingest.de.sentry.io/4509876543211
└─┬──┘ └──────────────┬───────────────┘ └──────────────┬─────────────────┘ └─────┬──────┘
scheme          public key                     org id + ภูมิภาค              project id
```

| ส่วน | ความหมาย |
| --- | --- |
| `scheme` | โปรโตคอล ควรเป็น `https` เสมอในการใช้งานจริง |
| `public key` | กุญแจสาธารณะของ Client Key (ดูได้ที่ Project Settings → Client Keys) |
| `host` | Self-hosted = โดเมนขององค์กร · SaaS = `o<org id>.ingest.<de หรือ us>.sentry.io` |
| `project id` | เลข ID ภายในของโปรเจกต์ ระบุว่า event ตัวนี้เข้าโปรเจกต์ไหน |

> 💡 **สังเกตว่าโครงสร้างเหมือนกันทุกประการ** ต่างแค่ส่วน host เท่านั้น การเปลี่ยนจาก SaaS ไป Self-hosted จึงแก้แค่ค่า DSN บรรทัดเดียว ไม่ต้องแก้โค้ดใด ๆ เลย

> 💡 **เคล็ดลับ:** ถ้ามี Client Key หลายตัวในโปรเจกต์เดียว จะได้ DSN คนละอันแต่ project id เดียวกัน วิธีนี้มีประโยชน์มากเวลาอยาก **เพิกถอน (revoke)** key ของแอปตัวใดตัวหนึ่งโดยไม่กระทบตัวอื่น เช่น แยก key ของ Mobile App ออกจาก Web

### 1.2.5 Workflow การใช้งานจริงในทีมพัฒนา

```
   [1] Deploy                [2] เกิดปัญหา             [3] แจ้งเตือน
Jenkins สร้าง Release  →  ผู้ใช้กดใช้งานแล้ว Error  →  Sentry ส่ง Alert เข้า
+ อัปโหลด Source Map      SDK จับและส่งเข้า Sentry       Slack/Teams/Email
        │                                                     │
        v                                                     v
   [6] ปิด Issue           [5] แก้ไข + Deploy         [4] วินิจฉัย
Sentry ตรวจว่าไม่เกิดซ้ำ  ←  ทีม Dev แก้แล้วออก      ←  เปิด Issue ดู Stack trace,
ใน Release ถัดไป              Release ใหม่               Breadcrumbs, Trace, Replay
```

> ✅ **ประเด็นสำคัญ:** ระบบ Monitoring จะมีคุณค่าจริง ก็ต่อเมื่อมัน **ปิดวงจร (close the loop)** ได้ คือ Error ที่แก้แล้วต้องถูก Resolve และถ้ากลับมาอีกต้องถูกจับได้ว่าเป็น **Regression** เราจะได้ลงมือทำเรื่องนี้ในวันที่ 3

### 1.2.6 Self-hosted กับ SaaS ต่างกันอย่างไร และทำไม BCEL ต้องใช้ Self-hosted

> ❓ **คำถามที่ทุกคนสงสัย:** Sentry มีบริการผ่านเว็บที่ sentry.io พร้อม dashboard ครบอยู่แล้ว ทำไมต้องมาติดตั้งเองให้ยุ่งยาก

**คำตอบสั้น: ไม่ใช่เรื่องฟีเจอร์ แต่เป็นเรื่องข้อมูลออกนอกประเทศ**

**ฟีเจอร์เหมือนกันเกือบทั้งหมด** เอกสารทางการของ Sentry เขียนไว้ตรง ๆ ว่า

> "consider self-hosted as the Business plan without any software limitations and no paid tier"

แปลว่า Self-hosted ได้ทุกอย่างของแพ็กเกจ Business (ราคา 80 USD/เดือนบนเว็บ) โดยไม่จำกัดจำนวนผู้ใช้ ไม่จำกัด event และไม่เสียค่า subscription

**สิ่งที่อยู่ใน error event หนึ่งตัว**

| ข้อมูล | ความอ่อนไหวสำหรับธนาคาร |
| --- | --- |
| Stack trace + ชื่อคลาส/เมธอด/บรรทัด | เปิดเผยโครงสร้างระบบภายใน |
| SQL query ที่รัน (จาก `sentry-jdbc` วันที่ 2) | เปิดเผย schema ของฐานข้อมูล |
| Breadcrumbs, request URL, header | อาจมีเลขบัญชี รหัสลูกค้า token |
| User context | PII ตามนิยามกฎหมายคุ้มครองข้อมูล |
| Session Replay (วันที่ 3) | **ภาพหน้าจอที่พนักงานเห็น** รวมยอดเงินและข้อมูลลูกค้า |

**เหตุผลที่ BCEL ต้องใช้ Self-hosted**

| # | เหตุผล | รายละเอียด |
| --- | --- | --- |
| 1 | **ไม่มีศูนย์ข้อมูลในภูมิภาค** | Sentry SaaS มีให้เลือกแค่สหรัฐอเมริกากับเยอรมนี ไม่มีในอาเซียนหรือลาว (ท่านเพิ่งเห็นด้วยตาตอนสร้าง organization เมื่อเช้านี้) |
| 2 | **เครือข่ายออกอินเทอร์เน็ตไม่ได้** | ระบบ CRM/ERP ของธนาคารมักอยู่ในโซนที่ปิดขาออก |
| 3 | **ต้นทุนคาดเดาได้** | SaaS คิดตามจำนวน event ระบบธนาคารที่ transaction เยอะ ถ้าเปิด tracing สูงจะพุ่งเร็วมาก |
| 4 | **ควบคุมระยะเก็บข้อมูลเอง** | ตั้งตามนโยบายธนาคารได้ ไม่ถูกจำกัดตามแพ็กเกจ |

**แต่ Self-hosted ก็มีราคาที่ต้องจ่าย (ต้องรู้ไว้ด้วย)**

| ข้อเสีย | รายละเอียด |
| --- | --- |
| ไม่มี SLA และไม่มี support | เอกสารระบุว่า "comes with no guarantees or dedicated support" ต้องพึ่งชุมชนบน Discord |
| ภาระดูแล | ประมาณ 30 containers, RAM 16 GB ขั้นต่ำ, ต้องอัปเกรดทุกไตรมาส, ต้อง backup เอง |
| **ไม่มี Seer (AI debugging agent)** | เพราะเป็น closed source |
| ไม่มี spike protection / spend allocation | ผูกกับระบบ billing ซึ่ง self-hosted ไม่มี |
| Symbolication ของ iOS/Android จำกัด | ไม่กระทบเรา เพราะเป็น Spring Boot + Angular |

**สรุปสำหรับหลักสูตรนี้**

```
ทักษะที่เราจะเรียนตลอด 3 วัน                    SaaS   Self-hosted
──────────────────────────────────────────────────────────────────
Instrument Spring Boot / Angular                 ✅        ✅
อ่าน Issue, Stack trace, Breadcrumbs             ✅        ✅
Distributed Tracing, หา N+1, Slow Query          ✅        ✅
Alerts, Dashboards, Discover                     ✅        ✅
Release Health, Source Maps, Suspect Commits     ✅        ✅
CI/CD ด้วย Jenkins + sentry-cli                  ✅        ✅
──────────────────────────────────────────────────────────────────
ติดตั้งและดูแล instance เอง (Module 3.8 วันที่ 3)    ❌        ✅
```

> ✅ **นี่คือเหตุผลที่เราออกแบบคอร์สแบบนี้:** ประมาณ 90% ของเนื้อหาใช้ได้กับทั้งสองแบบ เราจึงเรียนบน SaaS เพื่อให้ทุกท่านเป็น Owner ขององค์กรตัวเอง ทดลองได้เต็มที่ และเก็บบัญชีไว้ฝึกต่อได้หลังจบคอร์ส ส่วน **การลงมือติดตั้ง Self-hosted จริง** จะเป็นเนื้อหาปิดท้ายหลักสูตรในวันที่ 3 (Module 3.8) โดยท่านจะได้เซิร์ฟเวอร์ของตัวเองคนละเครื่อง

### 1.3.4 การวางหน้าบ้าน (Reverse Proxy + TLS)

ในการใช้งานจริงห้ามเปิดพอร์ต 9000 ตรง ๆ ให้วาง Nginx หรือ Load Balancer ขององค์กรไว้ด้านหน้าเสมอ

> 📋 **ส่วนนี้เป็นเทมเพลตสำหรับนำกลับไปใช้ที่ BCEL** ไม่ต้องรันวันนี้ ในห้อง Lab วันที่ 3 เราจะใช้ `http://...:9000` ตรง ๆ เพราะเป็นเซิร์ฟเวอร์ชั่วคราวที่ไม่มีโดเมนของตัวเอง

```nginx
# /etc/nginx/conf.d/sentry.conf
server {
    listen 443 ssl http2;
    server_name sentry.bcel.local;

    ssl_certificate     /etc/ssl/bcel/sentry.crt;
    ssl_certificate_key /etc/ssl/bcel/sentry.key;

    # Sentry รับ payload ขนาดใหญ่ได้ (source map, minidump)
    client_max_body_size 100m;

    location / {
        proxy_pass http://127.0.0.1:9000;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 300s;
    }

    # ให้ Load Balancer ตรวจสุขภาพที่ endpoint นี้
    location /_health/ {
        proxy_pass http://127.0.0.1:9000/_health/;
        access_log off;
    }
}
```

จากนั้นแก้ค่าใน `sentry/config.yml` ให้ตรงกับ URL จริง มิฉะนั้นจะเจอ error เกี่ยวกับ CSRF:

```yaml
# sentry/config.yml
system.url-prefix: 'https://sentry.bcel.local'
system.internal-url-prefix: 'http://web:9000'
mail.backend: 'smtp'
mail.host: 'smtp.bcel.local'
mail.port: 587
mail.username: 'sentry-notify@bcel.com.la'
mail.password: '<password>'
mail.use-tls: true
mail.from: 'sentry@bcel.com.la'
```

และเปิดการรับรู้ TLS จาก proxy ใน `sentry/sentry.conf.py`:

```python
SENTRY_USE_SSL = True
SESSION_COOKIE_SECURE = True
CSRF_COOKIE_SECURE = True
SOCIAL_AUTH_REDIRECT_IS_HTTPS = True
```

### 1.4.4 แนวคิด Release และความสำคัญ

**Release** คือป้ายบอกว่า "event นี้มาจากโค้ดชุดไหน" ซึ่งเปิดประตูสู่ความสามารถสำคัญ 4 อย่าง:

| ความสามารถ | ประโยชน์ |
| --- | --- |
| **Regression detection** | Issue ที่ปิดไปแล้วกลับมาใน release ใหม่ → Sentry เปลี่ยนสถานะเป็น Regression อัตโนมัติ |
| **Suspect Commits** | บอกว่า commit ไหนน่าจะเป็นต้นเหตุ (ต้องเชื่อม Git) |
| **Release Health** | วัด Crash Free Rate ของแต่ละ release |
| **Source Maps** | ผูก source map เข้ากับ release ที่ถูกต้อง |

รูปแบบชื่อ Release ที่แนะนำ:

```
<ชื่อโปรเจกต์>@<เวอร์ชัน>+<build/commit>

ตัวอย่าง:
  bcel-crm-backend@1.4.0
  bcel-crm-backend@1.4.0+a3f5c9d          ← มี git sha ต่อท้าย (แนะนำที่สุด)
  bcel-crm-frontend@1.4.0+build.187
```

Spring Boot มีวิธีทำอัตโนมัติ โดยเปิด git-commit-id plugin แล้ว Sentry จะอ่านค่าจาก `git.properties` ให้เอง:

```xml
<!-- pom.xml -->
<plugin>
  <groupId>io.github.git-commit-id</groupId>
  <artifactId>git-commit-id-maven-plugin</artifactId>
  <version>9.0.1</version>
  <executions>
    <execution>
      <id>get-the-git-infos</id>
      <goals><goal>revision</goal></goals>
      <phase>initialize</phase>
    </execution>
  </executions>
  <configuration>
    <generateGitPropertiesFile>true</generateGitPropertiesFile>
    <generateGitPropertiesFilename>
      ${project.build.outputDirectory}/git.properties
    </generateGitPropertiesFilename>
  </configuration>
</plugin>
```

> 💡 **ทำไมเรื่องนี้สำคัญมากในวันที่ 3:** ถ้าไม่มี Release ที่ถูกต้อง เราจะไม่มีทางตอบคำถามผู้บริหารได้ว่า "Release เมื่อวานทำให้ระบบดีขึ้นหรือแย่ลง"

### 1.4.5 Data Scrubbing และการปกป้อง PII (สำคัญมากสำหรับ BCEL)

Sentry มีการปกป้องข้อมูล **3 ชั้น** ควรใช้ทั้งหมดพร้อมกัน:

```
ชั้นที่ 1: ใน SDK (ในแอปเรา)          ← ข้อมูลไม่ออกจากเครื่องเลย ปลอดภัยสุด
    │  send-default-pii=false, beforeSend
    v
ชั้นที่ 2: ใน Relay (หน้าด่าน Sentry)  ← ข้อมูลออกจากแอปแล้ว แต่ยังไม่ถูกเก็บ
    │  Advanced Data Scrubbing rules
    v
ชั้นที่ 3: Server-side scrubbing        ← ก่อนบันทึกลงฐานข้อมูล
       Default scrubbers + custom fields
```

**ชั้นที่ 1 - ตั้งค่าใน SDK**

```properties
# application.properties
# ไม่ส่งข้อมูลส่วนบุคคลโดยอัตโนมัติ (IP, header, cookie)
sentry.send-default-pii=false
```

```java
// BcelDataScrubber.java - กรองข้อมูลอ่อนไหวก่อนส่งออกจากแอป
package la.com.bcel.crm.config;

import io.sentry.Hint;
import io.sentry.SentryEvent;
import io.sentry.SentryOptions;
import io.sentry.protocol.SentryException;
import org.springframework.stereotype.Component;

/**
 * ตัวกรองชั้นที่ 1: ทำงานในแอปของเราเอง ก่อน event จะออกจากเครื่อง
 * ใช้กับข้อมูลที่ห้ามออกนอกองค์กรเด็ดขาด เช่น เลขบัญชี เลขบัตรประชาชน
 */
@Component
public class BcelDataScrubber implements SentryOptions.BeforeSendCallback {

    // เลขบัญชี BCEL รูปแบบ 3 หลัก - 12 หลัก และเลขบัตรประชาชนลาว
    private static final String ACCOUNT_PATTERN = "\\b\\d{3}-\\d{12}\\b";
    private static final String ID_CARD_PATTERN = "\\b\\d{13}\\b";

    @Override
    public SentryEvent execute(SentryEvent event, Hint hint) {
        // 1) ไม่ส่งชื่อ server ออกไป (อาจเปิดเผยโครงสร้าง network ภายใน)
        event.setServerName(null);

        // 2) ปกปิดในข้อความของ captureMessage()
        if (event.getMessage() != null && event.getMessage().getFormatted() != null) {
            event.getMessage().setFormatted(mask(event.getMessage().getFormatted()));
        }

        // 3) ⭐ ปกปิดในข้อความของ exception ด้วย
        //    จุดนี้สำคัญมาก เพราะ unhandled exception จะมีข้อความอยู่ใน
        //    event.getExceptions() ไม่ใช่ event.getMessage() (ซึ่งเป็น null)
        //    ถ้าลืมส่วนนี้ เลขบัญชีใน exception message จะหลุดออกไปทั้งหมด
        if (event.getExceptions() != null) {
            for (SentryException ex : event.getExceptions()) {
                if (ex.getValue() != null) {
                    ex.setValue(mask(ex.getValue()));
                }
            }
        }

        // 4) ลบ tag ที่อาจมีข้อมูลส่วนบุคคล
        event.removeTag("customer_phone");
        event.removeTag("customer_email");

        return event;
    }

    private String mask(String text) {
        return text.replaceAll(ACCOUNT_PATTERN, "[ACCOUNT_REDACTED]")
                   .replaceAll(ID_CARD_PATTERN, "[ID_REDACTED]");
    }
}
```

> ⚠️ **บทเรียนสำคัญจากโค้ดนี้:** ผู้เริ่มต้นมักเขียน `beforeSend` ที่กรองเฉพาะ `event.getMessage()` แล้วเข้าใจผิดว่าปลอดภัยแล้ว ทั้งที่ Error ส่วนใหญ่ในระบบจริงคือ **unhandled exception** ซึ่งเก็บข้อความไว้ใน `event.getExceptions()` **ต้องกรองทั้งสองที่เสมอ** และควรทดสอบด้วย exception จริงไม่ใช่แค่ `captureMessage`

**ชั้นที่ 2–3 - ตั้งค่าใน UI ของ Sentry**

ไปที่ **Organization Settings → Security & Privacy** แล้วเปิด:

| ตัวเลือก | ค่าที่แนะนำสำหรับ BCEL |
| --- | --- |
| Require Data Scrubber | ✅ เปิด |
| Require Using Default Scrubbers | ✅ เปิด (กรอง password, secret, api_key, credit card อัตโนมัติ) |
| Global additional sensitive fields | `account_no, accountNumber, id_card, citizen_id, pin, otp, cvv, mobile_no, card_no` |

### 1.5.2 เพิ่ม Dependency ที่ถูกต้อง (ระวังสับสน)

Sentry มี artifact สำหรับ Spring Boot **สามตัว** ที่ชื่อคล้ายกันมาก การเลือกผิดคือปัญหาอันดับหนึ่งที่ผู้เรียนเจอ:

| Spring Boot เวอร์ชัน | artifactId ที่ต้องใช้ | Namespace ของ annotation |
| --- | --- | --- |
| Spring Boot 2.x | `sentry-spring-boot-starter` | `io.sentry.spring.tracing.*` |
| **Spring Boot 3.x (ที่เราใช้)** | **`sentry-spring-boot-starter-jakarta`** | `io.sentry.spring.jakarta.tracing.*` |
| Spring Boot 4.x | `sentry-spring-boot-4` | `io.sentry.spring7.tracing.*` |

```xml
<!-- backend/pom.xml -->
<properties>
    <java.version>21</java.version>
    <sentry.version>8.43.2</sentry.version>
</properties>

<dependencyManagement>
  <dependencies>
    <!-- BOM ช่วยให้ทุก artifact ของ Sentry ใช้เวอร์ชันเดียวกันเสมอ -->
    <dependency>
      <groupId>io.sentry</groupId>
      <artifactId>sentry-bom</artifactId>
      <version>${sentry.version}</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>

<dependencies>
  <!-- Sentry สำหรับ Spring Boot 3 (Jakarta EE) -->
  <dependency>
    <groupId>io.sentry</groupId>
    <artifactId>sentry-spring-boot-starter-jakarta</artifactId>
  </dependency>

  <!-- ส่ง log ระดับ ERROR เข้า Sentry และเก็บ log อื่นเป็น Breadcrumb -->
  <dependency>
    <groupId>io.sentry</groupId>
    <artifactId>sentry-logback</artifactId>
  </dependency>

  <!-- จำเป็นสำหรับ @SentryTransaction / @SentrySpan (เรียนวันที่ 2) -->
  <dependency>
    <groupId>org.springframework.boot</groupId>
    <artifactId>spring-boot-starter-aop</artifactId>
  </dependency>
</dependencies>
```

> ⚠️ **ตรวจเวอร์ชันล่าสุดเสมอ:** เลข `8.43.2` คือเวอร์ชัน ณ วันจัดอบรม ให้ตรวจเวอร์ชันล่าสุดได้ที่ [Maven Central: io.sentry](https://central.sonatype.com/artifact/io.sentry/sentry-spring-boot-starter-jakarta) ก่อนใช้งานจริงเสมอ
> 💡 **ทำไมต้องใช้ BOM:** เพราะเราจะเพิ่ม `sentry-jdbc` ในวันที่ 2 การใช้ BOM ทำให้ไม่ต้องระบุเวอร์ชันซ้ำ และไม่มีทางที่เวอร์ชันจะไม่ตรงกัน

```properties
# ค่านี้ทำให้ SentryExceptionResolver มีลำดับความสำคัญสูงกว่า resolver อื่น
# (เป็นค่าที่เอกสาร Sentry แนะนำ ใกล้เคียง Ordered.HIGHEST_PRECEDENCE = Integer.MIN_VALUE)
sentry.exception-resolver-order=-2147483647

# ไม่ต้องส่ง exception ที่เป็นเรื่องปกติของธุรกิจ
sentry.ignored-exceptions-for-type=\
  la.com.bcel.crm.common.BusinessValidationException,\
  org.springframework.web.servlet.NoHandlerFoundException

# ---------- Sentry: Performance (เปิดจริงในวันที่ 2) ----------
sentry.traces-sample-rate=${SENTRY_TRACES_RATE:1.0}

# ---------- Sentry: การแก้ปัญหาตอนติดตั้ง ----------
# เปิดเฉพาะตอน setup ครั้งแรก แล้วปิดทันที (log จะเยอะมาก)
sentry.debug=false

# ---------- Logback integration ----------
# ระดับที่จะกลายเป็น Breadcrumb
sentry.logging.minimum-breadcrumb-level=info
# ระดับที่จะกลายเป็น Event จริงใน Sentry
sentry.logging.minimum-event-level=error
```

**ตารางอธิบาย property ที่สำคัญ:**

| Property | ค่าที่ตั้ง | ทำไมต้องตั้งแบบนี้ |
| --- | --- | --- |
| `sentry.dsn` | จาก env | เปลี่ยนตามสภาพแวดล้อมได้โดยไม่ต้อง build ใหม่ |
| `sentry.send-default-pii` | `false` | นโยบายธนาคาร ห้ามส่ง IP/header/cookie อัตโนมัติ |
| `sentry.in-app-includes` | `la.com.bcel.crm` | ทำให้ Sentry เน้น stack frame ของโค้ดเรา ไม่ใช่ของ Spring |
| `sentry.exception-resolver-order` | `-2147483647` | ให้ Sentry ดักก่อน resolver อื่น ไม่งั้น exception ที่มี `@ExceptionHandler` จะไม่ถูกส่ง |
| `sentry.ignored-exceptions-for-type` | ระบุคลาส | ป้องกัน "noise" จาก error ที่เป็นเรื่องปกติทางธุรกิจ |
| `sentry.logging.minimum-event-level` | `error` | ถ้าตั้งเป็น `warn` จะได้ event ท่วมจนใช้งานไม่ได้ |

### 1.5.5 ทดสอบส่ง Error ตัวแรก

**วิธีที่ 1 - เขียน Controller สำหรับทดสอบ (ลบออกก่อนขึ้น production)**

```java
// backend/src/main/java/la/com/bcel/crm/config/SentryDebugController.java
package la.com.bcel.crm.config;

import io.sentry.Sentry;
import io.sentry.SentryLevel;
import org.springframework.context.annotation.Profile;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestMapping;
import org.springframework.web.bind.annotation.RestController;

/**
 * Controller สำหรับทดสอบการเชื่อมต่อ Sentry เท่านั้น
 * @Profile("!production") ทำให้ bean นี้ไม่ถูกสร้างบน production
 */
@RestController
@RequestMapping("/api/_debug/sentry")
@Profile("!production")
public class SentryDebugController {

    /** 1) ทดสอบ Unhandled Exception - Sentry ต้องจับได้เองโดยเราไม่ต้องเขียนอะไร */
    @GetMapping("/boom")
    public String boom() {
        throw new IllegalStateException("BCEL CRM: ทดสอบ unhandled exception ตัวแรก");
    }

    /** 2) ทดสอบ captureException - เราจับเองแล้วส่งเอง */
    @GetMapping("/capture")
    public String capture() {
        try {
            int result = 10 / 0;
            return "never reach here: " + result;
        } catch (ArithmeticException e) {
            Sentry.captureException(e);
            return "ส่ง exception เข้า Sentry แล้ว";
        }
    }

    /** 3) ทดสอบ captureMessage - ส่งข้อความธรรมดา ไม่ใช่ exception */
    @GetMapping("/message")
    public String message() {
        Sentry.captureMessage("BCEL CRM: ทดสอบส่งข้อความเข้า Sentry", SentryLevel.INFO);
        return "ส่งข้อความเข้า Sentry แล้ว";
    }
}
```

### 1.5.6 การจับ Unhandled Exception โดยอัตโนมัติ

Sentry Spring Boot Starter ทำงานเบื้องหลังผ่านกลไกเหล่านี้ (ไม่ต้องเขียนโค้ดเพิ่ม):

| กลไก | จับอะไร |
| --- | --- |
| `SentryExceptionResolver` | Exception ที่หลุดออกจาก Controller ของ Spring MVC |
| `SentryTracingFilter` | สร้าง Transaction ให้ทุก HTTP request (ใช้ในวันที่ 2) |
| `SentryUserFilter` | ผูกข้อมูลผู้ใช้จาก Spring Security (ถ้าเปิด `send-default-pii`) |
| `SentryLogbackAppender` | เปลี่ยน log ระดับ ERROR เป็น event และระดับต่ำกว่าเป็น breadcrumb |
| `SentryTaskDecorator` | ส่งต่อ scope ไปยัง `@Async` thread |

**ลำดับการทำงานเมื่อเกิด Exception:**

```
Request เข้ามา
    │
    ├─> SentryTracingFilter  เริ่ม Transaction "GET /api/customers/{id}"
    │       │
    │       ├─> Controller ทำงาน
    │       │       └─> Service โยน NullPointerException 💥
    │       │
    │       ├─> @ExceptionHandler (ถ้ามี) จับไว้แปลงเป็น HTTP 500
    │       │
    │       └─> SentryExceptionResolver ดักเก็บ exception ส่งเข้า Sentry
    │              (ทำงานได้เพราะเราตั้ง exception-resolver-order เป็นค่าต่ำสุด)
    │
    └─> Transaction จบ ส่งเข้า Sentry พร้อม status = internal_error
```

> ⚠️ **กับดักที่พบบ่อยมาก:** ถ้าทีมมี `@RestControllerAdvice` ที่ `catch (Exception e)` แล้วคืน `ResponseEntity` โดยไม่ทำอะไรต่อ **Sentry จะไม่เห็น exception นั้นเลย** ถ้าไม่ได้ตั้ง `sentry.exception-resolver-order` วิธีที่ชัวร์ที่สุดคือเรียก `Sentry.captureException(e)` เองใน handler:
>
> ```java
> @RestControllerAdvice
> public class GlobalExceptionHandler {
>
>     @ExceptionHandler(Exception.class)
>     public ResponseEntity<ApiError> handleAll(Exception e) {
>         // ส่งเข้า Sentry อย่างชัดเจน ไม่พึ่งการตั้งค่าเพียงอย่างเดียว
>         Sentry.captureException(e);
>         return ResponseEntity.status(500)
>                 .body(new ApiError("INTERNAL_ERROR", "เกิดข้อผิดพลาดภายในระบบ"));
>     }
> }
> ```

### 1.5.7 การแก้ปัญหาเมื่อ "ข้อมูลไม่เข้า Sentry"

ให้ไล่ตรวจตามลำดับนี้ (จากต้นทางไปปลายทาง):

| ลำดับ | ตรวจอะไร | คำสั่ง / วิธีดู |
| --- | --- | --- |
| 1 | DSN ถูกอ่านเข้ามาจริงไหม | ตั้ง `sentry.debug=true` แล้วดู log ตอนแอปเริ่ม ต้องเห็น `Initializing SDK with DSN` |
| 2 | เครื่องแอปติดต่อ Sentry ได้ไหม | `curl -v https://sentry.bcel.local/api/2/envelope/` |
| 3 | มี proxy/firewall กั้นไหม | ตั้ง `sentry.proxy.host` และ `sentry.proxy.port` |
| 4 | ใบรับรอง TLS ภายในองค์กร | import CA เข้า truststore ของ JVM ด้วย `keytool` |
| 5 | Relay รับ envelope ไหม | `docker compose logs -f relay` |
| 6 | Consumer ประมวลผลไหม | `docker compose logs -f ingest-consumer` |
| 7 | Rate limit เต็มไหม | Project Settings → Client Keys → ดู Rate Limit |
| 8 | Inbound filter บล็อกไหม | Project Settings → Inbound Filters |

```bash
# ทดสอบส่ง envelope ดิบ ๆ ด้วย curl เพื่อพิสูจน์ว่าเครือข่ายไม่มีปัญหา
curl -v -X POST \
  'https://sentry.bcel.local/api/2/store/?sentry_version=7&sentry_key=<public-key>' \
  -H 'Content-Type: application/json' \
  -d '{"message":"ทดสอบส่งตรงด้วย curl","level":"info"}'
# ควรได้ HTTP 200 พร้อม event id กลับมา
```

> 💡 **เคล็ดลับที่ใช้ได้ผลเสมอ:** ถ้า `curl` ส่งเข้าได้แต่แอปส่งไม่ได้ แสดงว่าปัญหาอยู่ที่ **แอป** (DSN ผิด, TLS truststore, proxy) แต่ถ้า `curl` ก็ส่งไม่ได้ ปัญหาอยู่ที่ **เครือข่ายหรือตัว Sentry**

### ขั้นที่ 6 - จัดระเบียบ Issue

ฝึกใช้งานพื้นฐานที่จะใช้ทุกวัน:

1. เลือก Issue ของ debug endpoint ทั้งหมด → กด **Ignore** (เพราะเป็นการทดสอบ ไม่ใช่ปัญหาจริง)

### 🧩 โจทย์ท้าทายเพิ่มเติม (สำหรับผู้ที่ทำเสร็จก่อน)

1. **แยก Environment จริง** ลองรันแอปด้วย `SENTRY_ENVIRONMENT=staging` แล้วยิง error ซ้ำ จากนั้นใช้ตัวกรอง `environment:staging` ใน Sentry ดูว่าเห็นเฉพาะชุดหลังหรือไม่
2. **ทดสอบ ignored-exceptions** สร้าง `BusinessValidationException` แล้วโยนออกมา ตรวจว่า Sentry **ไม่** สร้าง Issue ให้ (พิสูจน์ว่า property ทำงาน)
3. **ตั้ง Rate Limit** ที่ Project Settings → Client Keys กำหนด 100 events/นาที แล้วยิง error รัว ๆ 200 ครั้งด้วย `for i in {1..200}; do curl -s .../boom > /dev/null; done` สังเกตว่า Sentry ตอบ HTTP 429 และดูสถิติที่ Stats page
4. **ทดลองปิด in-app-includes** ลบ property `sentry.in-app-includes` แล้วยิง error ใหม่ เปรียบเทียบว่า Stack trace อ่านยากขึ้นแค่ไหน

| หัวข้อ | ผลลัพธ์ที่จับต้องได้ |

### คำสั่งที่ควรจำ

**บนโน้ตบุ๊กของท่าน**

```bash
# --- รันแอป ---
export SENTRY_DSN='...' SENTRY_ENVIRONMENT=development
export DB_USER='crm_app' DB_PASSWORD='labpass123'
mvn spring-boot:run

# --- ทดสอบ ---
curl -i http://localhost:8080/api/_debug/sentry/boom

# --- ตรวจฐานข้อมูล (ต้องอยู่ในโฟลเดอร์ bcel-crm-lite) ---
cd bcel-crm-lite && docker compose exec mariadb mariadb -u crm_app -plabpass123 bcel_crm -e "SHOW TABLES;"
```

**บนเซิร์ฟเวอร์ Self-hosted (ใช้ตอนกลับไปดูแลระบบจริงที่ BCEL)**

```bash
cd ~/self-hosted                        # หรือ path ที่โคลน repository ไว้
docker compose ps                       # สถานะบริการ
docker compose logs -f relay            # ดูว่า event เข้าถึง Sentry ไหม
docker compose logs -f ingest-consumer  # ดูว่า event ถูกประมวลผลไหม
docker compose run --rm -T web sentry export > backup.json
```

### 🔮 พรุ่งนี้เราจะทำอะไร (วันที่ 2)

พรุ่งนี้เราจะยกระดับจาก "เห็น Error" ไปสู่ "วินิจฉัยได้ว่าเกิดกับใคร ตอนไหน และช้าที่ชั้นไหน":

- **เช้า:** Issue Grouping และ Fingerprinting, การเพิ่ม User Context / Tags / Breadcrumbs ให้ Error มีบริบทครบ
- **บ่าย:** Performance Monitoring, ผูก `sentry-jdbc` เพื่อเห็นทุก Query ของ MariaDB เป็น Span, ติดตั้ง `@sentry/angular` และเชื่อม Distributed Tracing แบบ End-to-End จากปุ่มบนหน้าจอไปจนถึง SQL
